# Architectural Decisions Log

This document tracks specific engineering decisions made on the Gimbal project.

> **⚠️ Entries 1–4 are historical and superseded by [ADR-003](adr/ADR-003.md).** They describe decisions made
> inside the retired **Python** core (FastAPI/SQLAlchemy/Pydantic/rapidfuzz). Gimbal is now a single-language
> **TypeScript on Node** project; the Python tree is a reference-only executable spec, deleted once parity
> is verified. Read entries 1–4 for motivation only — their file paths and technologies no longer exist.
> Current decisions start at entry 5.

## 1. Split Monolithic Recorder into Feature Domains (2026-07-04) — *superseded by ADR-003*

**Context:** The old repository contained an `gimbal_recorder` directory that, despite its name, housed the entire backend (FastAPI server, SQLAlchemy db, execution engine, and recording logic).

**Decision:** Instead of copying the entire directory into `packages/core/recorder`, the monolithic structure was split into its proper feature domains to align with the HLD v3.1:
- `core/recorder`: Only StateAwareRecorder, DOM snapshots, and Playwright interaction observers.
- `core/execution`: Playwright test engine and test generators.
- `core/server`: FastAPI API layer.
- `core/db`: SQLAlchemy storage layer.

**Rationale:** The HLD strictly specifies a modular platform with separation of concerns. This split ensures the backend is feature-based and highly decoupled, preventing circular dependencies.

## 2. Shared Models as Source of Truth (2026-07-04)

**Context:** Both `gimbal_recorder` and `gimbal-resolvers` had duplicate definitions for models like `DOMElement` and `ActionNode`.

**Decision:** A centralized `packages/core/models/` module was established to house all Pydantic schemas and dataclasses.

**Rationale:** Unified execution (UI vs. API) requires a single source of truth for test definitions.

## 3. Removal of `sys.path` Injection for Resolvers (2026-07-04)

**Context:** The old execution engine used a hack (`sys.path.insert(0, _RESOLVERS_DIR)`) to dynamically inject the `gimbal-resolvers` package at runtime.

**Decision:** The resolvers and execution engine were co-located within the single `core` package (`core.resolvers` and `core.execution`), and the `sys.path` hack was replaced with standard relative package imports.

**Rationale:** Dynamic path injection breaks static type checking, makes testing brittle, and violates standard Python packaging conventions.

## 4. Consolidated Dependencies in `gimbal-core` (2026-07-04)

**Context:** The old setup relied on a `pyproject.toml` for the API and a separate `requirements.txt` for the resolvers.

**Decision:** Dependencies were merged into a single `packages/core/pyproject.toml` containing `playwright`, `fastapi`, `sqlalchemy`, and `rapidfuzz`. The package name was updated to `gimbal-core`.

**Rationale:** A unified `core` package ensures all dependencies resolve correctly during installation in a single virtual environment without conflicts.

## 5. Single-Language TypeScript Stack (2026-07-10)

**Context:** The three-language split (Bun/TS CLI, ~21.6k-line Python core, separate Next.js dashboard) imposed a permanent schema-duplication and Playwright-subprocess tax on a pre-1.0, IR-driven project.

**Decision:** Rebuild as one TypeScript-on-Node monorepo (`shared` Zod IR, `core` Fastify, `cli` commander+MCP, `dashboard` Vite SPA bundled into core). Fuzzy matching (`rapidfuzz`) is replaced by a local fixed-weight ONNX embedding model + cosine similarity. Full rationale and alternatives in [ADR-003](adr/ADR-003.md); build order in [PLAN-001](PLAN-001.md). Supersedes entries 1–4.

**Rationale:** One language, one runtime, one shared IR eliminates Pydantic↔Zod drift; Playwright runs natively; `npx gimbal` is the only install step.

## 6. Runtime Locate Ladder is Cache-First (2026-07-15)

**Context:** The LLDs disagreed on where the runtime fast-path selector is read from — the `resolution_cache` table (LLD-007) vs. the grounded artifact (LLD-005) — leaving healed selectors written to a cache nothing consulted and the same step re-healing every run.

**Decision:** The locate ladder is **selector cache (keyed by `(testId, stepId, domHash)`) → grounded-artifact selector → runtime heal → stale**. The SQLite cache is the fast path; the versioned artifact is the durable seed used when the cache is cold or the page changed. A confident runtime heal writes to the cache (never the versioned artifact), so the next run on the changed page hits cache. See LLD-005 §4, LLD-006 §3, LLD-007 §4.

**Rationale:** Preserves the "deleting `cache.db` loses only speed" invariant while making heals actually stick, and keeps runtime writes off the git-versioned artifacts.

## 7. Affordance is a Gate, Not a Weighted Signal (2026-07-15)

**Context:** LLD-004 both hard-filtered candidates on affordance *and* gave affordance weight 0.1 as a 0/1 value. Every surviving candidate scored 1, adding a constant offset that silently skewed scores against the absolute band thresholds.

**Decision:** Affordance is purely the pre-scoring gate. The weighted signals are `semantics 0.45 · context 0.33 · structure 0.22` (sum 1.0); index remains a tiebreak, unweighted. See LLD-004 §5.

**Rationale:** A constant contributor carries no discriminative value and only distorts banding; removing it makes the final score a clean blend of the informative signals.

## 8. Grounded Test Stores the Winner Only (2026-07-15)

**Context:** The grounded artifact embedded the full ranked candidate list, duplicating `candidates.json` and putting volatile per-candidate DOM data into the durable, git-versioned tier — the very churn ADR-002 rejected `flow.json` for.

**Decision:** The versioned grounded test stores a **winner-only** resolution (selected candidate + anchors); the full ranking stays in `candidates.json`. `GroundedTarget.resolution` is optional so partially grounded tests (halted at the first ungrounded step) validate. See LLD-001 §6.

**Rationale:** Keeps the durable artifact small and stable across UI reshuffles; a partial grounding pass must still round-trip through the schema for review.

## 9. Maintenance Heal Entry Point; Negative-Test Flag in the IR (2026-07-15) — *`patchedSpec?` superseded by entry 10*

**Context:** SPEC-005 had the agent author repairs while the `updateTest` tool had nowhere to put a repaired spec, and LLD-006 called an undefined `llmRepair()`. Separately, negative tests were specced (verdict inversion) but had no representable field in the IR.

**Decision:** (a) `maintain(testId, stepIds, patchedSpec?)` — agent path passes the patched `SpecIR` via `updateTest`/`POST /tests/:id/maintain`; CLI path omits it and core calls a provider through `AuthoringService.repair()`. **This CLI/provider branch was removed the same day — see entry 10.** (b) Add `negative: boolean` to the step schema; the assertion engine inverts the verdict when set. This part stands. See LLD-006 §6, LLD-002, LLD-008, LLD-001 §3, SPEC-003 §6, SPEC-004 §4.

**Rationale:** Specced behavior must have a home in the schema (the negative-test half of this decision). The maintenance-heal half was corrected almost immediately — see entry 10 for why.

## 10. Gimbal Never Calls an LLM Provider — Authoring Is Agent-Only (2026-07-15)

**Context:** Entry 9 (and, before it, `SPEC-001`/`LLD-002`/`LLD-008`/`LLD-009` as originally drafted) described **two** authoring/maintenance paths: an "agent path" where a connected coding agent authors the spec and calls `submitSpec`/`updateTest`, and a "CLI/provider path" where a bare `gimbal author "<intent>"` invocation had core call a configured LLM provider (Anthropic/OpenAI) directly, holding an API key in `GimbalConfig.llm` and billing the developer's own provider account per call. This was built and briefly shipped (`AnthropicLlmClient`, `packages/core/src/authoring/llm-client.ts`, `gimbal_LLM_API_KEY`) before being caught as a misread of the original intent: **Gimbal was never meant to hold a provider client at all.** The only intended authoring mechanism is the developer's own already-running coding agent (Claude Code, Cursor, ...), interacting with Gimbal exclusively through MCP.

**Decision:** Remove the CLI/provider path entirely. `AuthoringService` now has one way to create a spec — `submit(spec)` — which validates and stores a spec the caller (always an agent) already authored. `HealingService.maintain(testId, stepIds, patchedSpec)` now requires `patchedSpec`; there is no core-side fallback that generates one. `GimbalConfig` has no `llm` block and no API key anywhere. The `authorTest` MCP tool and `gimbal author` CLI command are removed; `gimbal heal` becomes read-only (prints the repair payload instead of attempting a repair). See `SPEC-001` §2, `LLD-002`, `LLD-006` §6, `LLD-008` §2–3, `LLD-009` §2.

**Rationale:** The product's entire value proposition is that intelligence lives in authoring and nowhere else runtime-adjacent (ADR-001) — but *whose* intelligence was never meant to be Gimbal's own provider bill. The developer already has an LLM session open to talk to Gimbal in the first place; giving Gimbal a second, independent path to call a model directly duplicates cost, duplicates the trust boundary (a second API key to secure), and contradicts the "no vendor lock-in, nothing leaves your machine unless you already sent it somewhere" positioning. One entry point, held to one already-trusted actor, is simpler and is what was actually intended.

## 11. Dashboard Static Serving Needs an SPA Fallback (2026-07-24)

**Context:** Implementing LLD-010's nested client routes (`/tests/:id/runs/:runId`, `/reviews/:testId/:stepId`) surfaced a gap the original single-view dashboard never hit: `@fastify/static` only serves files that exist on disk, so any deep link into a client-side `wouter` route 404ed instead of loading the SPA shell. Verified live — before the fix, `GET /tests/:id/runs/:runId` returned Fastify's default 404 JSON; only `GET /` worked.

**Decision:** `packages/core/src/server/app.ts` registers a `setNotFoundHandler` that serves `index.html` for any unmatched `GET` request except under `/screenshots/*` (the second static root, whose own 404s must stay real 404s for missing screenshot files). All REST routes are flat (see `routes.ts` — one path param, no further nesting), so any unmatched GET is unambiguously a client route, not a mistyped API call.

**Rationale:** A dashboard whose core pitch is deep-linkable URLs ("a developer can paste a run link to a teammate," LLD-010 §3.1) is broken if pasting that link 404s. The fallback is scoped narrowly (GET-only, screenshot root excluded) so it can't mask a genuinely missing REST resource — those still reach their own route handler and return a typed `ApiError`.

## 12. REST API Moves Under `/api` — Dashboard Routes Own the Bare Paths (2026-07-24)

**Context:** Building LLD-010's dashboard against the live server (not just typechecking it) surfaced that its client-side route map — `/tests`, `/tests/:id`, `/tests/:id/runs`, `/reviews` — is byte-for-byte identical to four existing REST routes in `routes.ts`. Since those routes are real, registered Fastify handlers, they matched *before* the entry 11 SPA fallback ever got a chance to run: visiting `/tests` in a browser rendered a raw JSON array, not the test list page. Screenshotted and confirmed live (`GET /tests` returned `application/json`, four of six dashboard pages showed JSON instead of the app) before this was understood as a routing collision rather than an app bug.

**Decision:** Every existing REST route moves under an `/api` prefix — `routes.ts` now wraps its handlers in `app.register(fn, { prefix: "/api" })`, so `GET /tests` becomes `GET /api/tests`, `POST /runs` becomes `POST /api/runs`, etc. `/health` stays unprefixed (bare liveness-probe convention). `packages/cli/src/client.ts` (`CoreClient`, the only other caller — used by both the CLI commands and the MCP tool handlers) and the dashboard's `api.ts`/`vite.config.ts` dev proxy were updated to match. The entry-11 SPA fallback's server-path exclusion list is now just `/api/*` and `/screenshots/*`. WebSocket routes (`/ws/runs/:id`, `/ws/ground/:id`) were left unprefixed — nothing outside the dashboard calls them directly and none collide with a dashboard page path.

**Rationale:** The dashboard and the REST API it calls cannot share a flat, unprefixed URL space once the dashboard has more than a couple of top-level pages — new dashboard routes will keep colliding with new REST routes (or vice versa) as both grow. Prefixing the API is the conventional fix for "one origin serves both a JSON API and an SPA" and required touching every route string exactly once (via Fastify's `prefix` option) rather than auditing collisions by hand each time either surface adds a path.

## 13. Full Rebrand from gimbal to Gimbal (2026-07-27)

**Context:** The product name was changing from gimbal to Gimbal. The old name was load-bearing in more places than prose: the npm workspace scope (`@gimbal/core`, `@gimbal/cli`, `@gimbal/shared`, `@gimbal/dashboard`), the CLI binary name (`gimbal`), an exported type (`gimbalConfig`), an env var (`gimbal_PORT`), and the default local-state directory/config filename (`.gimbal/`, `gimbal.config.json`).

**Decision:** Renamed every live-code and docs reference: workspace scope to `@gimbal/*`, CLI bin to `gimbal`, `gimbalConfig` to `GimbalConfig`, `gimbal_PORT` to `GIMBAL_PORT`, and the default local-state path/config name to `.gimbal/`/`gimbal.config.json`. Regenerated `pnpm-lock.yaml` via `pnpm install` and rebuilt every package rather than hand-editing `dist/` or the bundled dashboard static assets under `packages/core/static/`, since both are build artifacts. Left the repo's own root directory name (`gimbal/` on disk) and historical references to the old `gimbal_recorder` directory in this log's earlier entries untouched — the former is an unrelated filesystem detail, the latter is a historical record of what existed at the time and would misrepresent past entries if edited.

**Rationale:** A rename that only touches prose strings leaves the package manager, the CLI's own `--help` output, and a project's on-disk config directory still announcing the old name — the branding would be inconsistent at the exact surfaces users interact with first. Rebuilding instead of hand-patching `dist/`/static output keeps generated artifacts honest reflections of source, matching how the project already treats build output elsewhere.

## 14. KDG v1: Static-Analysis-Only, Next.js App Router, No Conditional Taxonomy (2026-07-27)

**Context:** ADR-002 named the KDG (parent/child + conditionals, authoring/repair-time context) but explicitly deferred its data structure and construction algorithm (§6, Out of Scope, Action Item 8). Design discussion established the actual constraint: KDG re-runs must be cheap enough that an agent doesn't need to re-read the whole frontend on every authoring/healing pass, which only matters once a codebase is large enough that re-reading it is unreliable or exceeds context. Research into React/Next.js conditional-rendering static analysis found no existing open-source tool does this; the TS Compiler API (already a dependency) can reliably extract JSX parent/child structure and locate conditional branches, with a hard ceiling at runtime-only data (network-fetched flags, request-time middleware) that no static or agentic reading of source can resolve. Direct reasoning about the KDG's sole consumer — an LLM coding agent authoring/repairing tests — concluded a pre-classified conditional taxonomy (`kind: "role" | "featureFlag" | ...`) adds a way for Gimbal to be wrong about something the agent can interpret from raw expression text just as well.

**Decision:** KDG v1 (ADR-004, SPEC-006, LLD-011) is Next.js App Router-only for v1, discovered by filesystem convention (`app/**/page.tsx`/`layout.tsx`/`route.ts` + transitive local imports), with zero LLM calls anywhere in construction. Every conditional branch resolves to one of three states, not a binary known/unknown: `resolved` (raw expression, safely traced), `needs_trace` (raw expression + a pointer — file path, line, one-line instruction — to exactly where an agent should look next), or `unknown` (genuinely runtime-only, no file resolves it). Construction triggers from `getMap`/`getDelta` MCP calls (not a background watcher), gated by a per-file content-hash manifest so unchanged source short-circuits to a cache hit and changed files trigger only per-file node replacement, not a full rebuild. `getMap` returns a single route's transitive subgraph, never the whole app. Storage is SQLite-only in the existing `.gimbal/cache.db` (new `kdg_nodes`/`kdg_manifest`/`kdg_versions` tables) — fully regenerable, not git-versioned, same invariant as the resolver's selector/embedding cache.

**Rationale:** A knowledge graph only earns its construction cost if querying it is cheaper than an agent re-deriving the same facts from source — that requires both construction and reads to stay cheap, which per-file incremental rebuilds and route-scoped responses deliver and a full-rebuild/whole-graph design would not. Dropping the conditional taxonomy in favor of raw-expression-plus-pointer keeps Gimbal from fabricating a classification it can't verify, consistent with the project's existing "never guess, mark for review" posture (ADR-001/002, SPEC-004 §3) — the KDG tells the agent where the answer lives when it can't tell it the answer itself.

## 15. Agent-Facing Documentation Lives in MCP Tool Descriptions Plus a Companion Skill (2026-07-28)

**Context:** MCP tool schemas in `packages/cli/src/mcp/server.ts` had one-word-per-field annotations (e.g. bare `z.string()` params) and no `description` on any registered tool, so a connected coding agent had no in-band guidance on authoring rules (DOM-blind targets, vars vs. secrets), when to call `groundTest` vs. `healing` vs. `updateTest`, or how to interpret `stale`/`ungrounded`/confidence bands. `docs/USING_GIMBAL_IN_ANOTHER_REPO.md` documents setup, not usage, and per-repo docs aren't visible to an agent unless it happens to read them.

**Decision:** Every tool in `buildMcpServer` was converted from the deprecated positional `server.tool(name, shape, cb)` form to `server.registerTool(name, { description, inputSchema }, cb)`, with a condensed, agent-actionable description per tool (what it does, when to call it, what to do with common failure states) and a `.describe()` on every scalar input field. A companion skill, `.claude/skills/gimbal/SKILL.md`, was added covering the end-to-end workflow (author → ground → run → heal), the DOM-blind authoring contract, how to read grounding/run-report failure states, and explicit "never do this" boundaries (no selectors, no secrets in specs, no healing an assertion failure). No em dashes, per house style for this doc.

**Rationale:** Tool descriptions are what an agent sees at the moment it decides which tool to call (`tools/list`), so they need to be self-sufficient for correct, single-call usage without prior context. A skill is loaded once at task start and can hold the workflow-level judgment (ordering, common failure diagnosis, hard boundaries) that would bloat every individual tool description if duplicated there. Splitting the two keeps each doing the job the other can't, rather than cramming both into one artifact.

## 16. Split `gimbal start` Into `start` (Human) and `mcp` (Agent) (2026-07-28)

**Context:** `gimbal start` did three unrelated things at once: spawn core (unconditionally, no liveness check), open the dashboard in a browser tab, and host the MCP stdio server. `docs/USING_GIMBAL_IN_ANOTHER_REPO.md` (and, following it, real usage) registered this same command with `claude mcp add gimbal -- node .../index.js start`. MCP clients spawn their registered command fresh on every new session or reconnect, not once per machine, so each new Claude Code session (and some reconnects within a session) re-ran the entire bundle: a fresh `open()` call fired every time, producing a new dashboard tab per session, and a second core process could spawn alongside an already-running one since `startCore` had no check for an existing instance. Verified live: every new chat window against a repo with Gimbal registered opened another dashboard tab.

**Decision:** `core-process.ts` gained `isCoreAlive(config)`, a `/health`-endpoint check. `gimbal start` is now idempotent: it calls `isCoreAlive` first and only spawns core if that returns false, then always opens the dashboard (this command is for a human invoking it directly, so opening the dashboard once per invocation is the expected behavior, not the bug). A new command, `gimbal mcp`, was added as the dedicated MCP entrypoint: it checks `isCoreAlive`, silently spawns core in the background only if not already running, hosts the MCP stdio server, and never calls `open()`. `docs/USING_GIMBAL_IN_ANOTHER_REPO.md`'s registration example, and every other doc describing the old single-command lifecycle (README, AGENTS.md, PLAN-001, ADR-002/003, LLD-000/008/009, SPEC-005, WALKTHROUGH.md), were updated to register `gimbal mcp` instead of `gimbal start` and to describe the two entrypoints separately. `gimbal stop` needed no change: `startCore` writes the same pidfile regardless of which command invoked it, so it tears down a core spawned by either path.

**Rationale:** This is the standard shape used by other stdio MCP servers that front a stateful backend (Docker's MCP gateway, Playwright MCP, and similar): the process an MCP client spawns per session must be cheap, idempotent, and free of user-facing side effects, while the actual long-lived service it talks to is a singleton started and made visible (dashboard, GUI, whatever) through an explicit, separate, human-invoked command. Conflating the two meant every MCP handshake carried the cost and side effects of a full human-facing `start`, which is not what "an agent connected" should ever imply.

## 17. CSS/XPath-Escape All Selector Fragments Built From Live DOM Values (2026-07-28)

**Context:** A test run against a target app using shadcn/ui forms failed to ground any spec: React's `useId()` (which shadcn's `Form` component uses for field ids) produces ids containing `:` (e.g. `:r1:-form-item`), and `gate.ts`'s `durableSelector()` interpolated `winner.anchors.attributes.id` directly into `` `#${id}` `` with no escaping. `:` is CSS syntax (pseudo-classes), so the resulting selector was invalid CSS and threw inside Playwright's `page.locator()`, surfacing as an uncaught error the route's error handler mislabeled as a generic `"validation"` 500. A follow-up audit found this wasn't isolated: every selector-construction site in `packages/core` — `gate.ts`'s `data-testid` tier, and `dom-extractor.ts`'s `cssSelectorFor`, `xpathFor`, `contextPathFor`, and the `label[for=...]` accessible-name lookup — built CSS or XPath fragments by raw string interpolation of live DOM values (`id`, `data-testid`, `type`) with no escaping anywhere in the codebase. Beyond crash-only cases (invalid syntax throws), attribute values containing a literal `"` (e.g. a crafted `data-testid`) could break out of the attribute-value string and be reparsed as additional selector syntax — a selector-injection path that silently changes which element a step resolves to, not just a crash.

**Decision:** Added `packages/core/src/grounding/selector-escape.ts`, a Node-side `cssEscape()` (implementing the CSSOM `CSS.escape` algorithm, since Node has no native `CSS` global) plus an `xpathLiteral()` helper (the standard XPath `concat()` trick, since XPath has no native escape function). `gate.ts`'s `durableSelector()` now escapes both the `testId` and `id` anchors before interpolating them. `dom-extractor.ts` runs serialized inside `page.evaluate()` (per its own file-level constraint, it can't import a module-scope helper — everything must be declared inside the evaluated function), so it uses the browser's native `CSS.escape` directly at each of its sites (`cssSelectorFor`'s id/testId/type branches, `contextPathFor`'s id fragment, the accessible-name `label[for=...]` lookup) and an inlined equivalent of `xpathLiteral` for `xpathFor`'s id branch. Added `gate.test.ts` covering the `useId()`-shaped-id crash case, the quote-injection case, tier precedence, and the no-anchor fallback — `gate.ts` had no prior test coverage.

**Rationale:** The gap was total rather than inconsistent — no escaping utility existed anywhere in `packages/core` or `packages/shared` before this — which pointed to a systemic cause rather than one missed line: `dom-extractor.ts`'s page-context constraint means a shared helper can't simply be imported there, so the path of least resistance had been "don't escape" at every site, consistently. Fixing only the one reported crash site would have left the selector-injection sites (`data-testid`, `type`) and the other crash sites (the `label[for=...]` lookup, which runs during extraction for every interactive element on the page, not just a resolved winner, and so has the widest blast radius of all of them) unfixed. Escaping at the point of interpolation, in both the Node and in-page contexts, closes the gap without changing the resolver's tier priority or selector format for any already-safe id/testid/type value.

## 18. Wait for Navigation Before Evaluating URL-Based Outcomes/Assertions (2026-07-28)

**Context:** `execution/adapters/ui.ts` captured `urlBefore` before dispatching an action, then evaluated `expectedOutcome`/`assertions` immediately after `act()` resolved, with zero `waitForURL`/`waitForNavigation`/`waitForLoadState` calls anywhere in `packages/core/src`. Playwright's `locator.click()` only waits for the click event to dispatch, not for any resulting navigation — for a form whose submit triggers a server-action redirect (sign-in, sign-up, delete-confirm), the server-side work can still be in flight when the very next assertion reads `page.url()`. This produced a race: flows were reported as failed (`urlContains`/`navigation` outcome not yet true) even when the server action had already succeeded (verified independently — sessions/accounts were actually present in the target app's database despite the "failed" report). Because grounding replays the same step sequence to observe later DOM states, a stuck sign-in step meant grounding never advanced far enough to see the real signed-in page, so re-grounding a downstream step (e.g. sign-out) kept landing on the wrong element — not a resolver bug, a consequence of this race further upstream.

**Decision:** Added `expectsNavigation(step)` (true when a step's `expectedOutcome` includes `navigation`/`url_change`, or an assertion is `urlContains`) and `awaitNavigationIfExpected(step, page, urlBefore)` to `ui.ts`, called right after `act()` succeeds and before the outcome/assertion evaluation loops. It only waits when the step actually declares a navigation-shaped expectation — waiting unconditionally after every click would stall non-navigating interactions for no reason — and it waits via `page.waitForURL(url => url !== urlBefore, { waitUntil: "load" })`, bounded by the page's existing default navigation timeout (`config.timeouts.navMs`, already set globally in `playwright.ts`'s `openSession`), with the rejection swallowed rather than thrown so a step that legitimately never navigates (e.g. a negative test where the server correctly rejects) fails on the outcome/assertion check as before rather than throwing a different error. Added `ui.test.ts` (previously no coverage existed for this file) covering `expectsNavigation`'s four branches and `awaitNavigationIfExpected`'s wait/skip/timeout-swallow behavior via a minimal fake `Page`.

**Rationale:** A blind `waitForTimeout` sleep would be both slower than necessary (always pays a fixed delay) and still flaky (a slow server action could exceed a fixed sleep); gating the wait on whether the step actually expects a URL change, and waiting for the real condition rather than a duration, fixes the race without slowing down the majority of steps that don't navigate. Reusing the already-configured `navMs` timeout (rather than introducing a new per-step timeout field) keeps this consistent with how navigation timeouts are handled everywhere else in the execution engine.

## 19. Backfill Test Coverage Across Core's Previously-Untested Subsystems (2026-07-29)

**Context:** An earlier audit ([entry 17](docs/DECISIONS.md), [entry 18](docs/DECISIONS.md)) found that roughly two-thirds of `packages/core`'s functional surface had zero automated test coverage: the global error handler, the SQLite cache store, assertion/action execution, DOM extraction, healing, storage, the step dispatcher, and several smaller helper modules. The user asked for tests across all of it, prioritizing four named files (`server/app.ts`'s error handler, `cache/index.ts`, `execution/assert.ts` + `act.ts`, `grounding/dom-extractor.ts`) plus combined coverage for the remaining smaller untested pieces.

**Decision:** Added 16 new test files (`app.test.ts`, `cache/index.test.ts`, `execution/assert.test.ts`, `execution/act.test.ts`, `grounding/dom-extractor.test.ts`, `grounding/selector-escape.test.ts`, `execution/verdict.test.ts`, `execution/adapters/api-db.test.ts`, `execution/locate.test.ts`, `healing/healing.test.ts`, `grounding/grounding-helpers.test.ts`, `storage/layout.test.ts`, `storage/index.test.ts`, `server/ws-hub.test.ts`, `authoring/authoring.test.ts`, `execution/dispatcher.test.ts`), taking core from 10 test files / 93 tests to 27 / 259, all passing, with a clean typecheck across all four packages. Added `jsdom` as a core devDependency (scoped to `dom-extractor.test.ts` alone via a per-file `// @vitest-environment jsdom` directive, so every other test file stays on the default Node environment) since `dom-extractor.ts`'s DOM-manipulation logic can only be genuinely exercised against a real DOM tree, and polyfilled `CSS.escape` in that one file (jsdom, unlike a real browser, doesn't implement it) using the same CSSOM algorithm as `selector-escape.ts`'s Node-side `cssEscape`.

Testing this surface surfaced two more real bugs, fixed alongside the tests that caught them:
- **`server/app.ts`: `setErrorHandler` was registered after `registerRoutes()`.** Since `/api` routes live inside their own encapsulated Fastify child-plugin context, an error handler set on the parent *after* that child context is already closed never applies to it — every `/api` route was silently falling back to Fastify's own default error shape (`{statusCode, error, message}`) instead of the app's `ApiError` DTO shape, for the entire lifetime of the server. Fixed by moving `setErrorHandler` before `registerRoutes()`.
- **`server/app.ts`: the error handler mislabeled every non-validation error as `"validation"`** (the bug the user originally flagged) — fixed by checking `err.name === "ZodError"` / Fastify's own `.validation` array before choosing the response code, and added a new `"internal"` value to `ApiError.code`'s enum (`packages/shared/src/schema/dto.ts`) for the non-validation case, since no existing enum value meant "something else broke server-side" and the other values (`ungrounded`, `stale`, `browser_error`) are domain-specific concepts already used elsewhere.

**Rationale:** Both bugs were only findable by actually exercising the code through Fastify's real request/response pipeline (`app.inject()`) rather than reasoning about the handler function in isolation — a unit test of the error-classification logic alone would have passed against the exact same broken registration order, since it never would have gone through `registerRoutes()`'s encapsulation boundary. This is the concrete argument for backfilling coverage here rather than treating "add tests" as a mechanical checkbox: the act of writing a real test against the real wiring is what surfaced a bug worse than the one already known about.

## 20. Resolver/Authoring QA Pass: Seven Fixes From a Findings Report (2026-07-31)

**Context:** A comprehensive QA pass over the resolver and authoring surface produced seven findings, backed in the top case by real artifact data from a test repo. The most severe: `grounding/index.ts` never verified that a `navigate` step actually landed on its intended URL — Playwright's `page.goto()` resolves successfully even when a server-side redirect (an auth guard) bounces the page elsewhere, so grounding silently continued extracting candidates against the wrong page. Confirmed in production data: a `navigate-new-note` step targeting a guarded route got redirected to `/sign-in`, and every downstream step (title, body, delete confirm) then grounded against sign-in-page elements with no error and no low-confidence flag — the defect surfaced three steps later as an unrelated assertion failure. Six more findings followed: (2) `banding.ts`'s sibling-index tiebreak used `contextPath[0]` (tag + optional id) as a same-parent proxy, which collapses to the same string (`"div"`) for any two unrelated, unid'd wrapper elements; (3) `elementVisible`/`elementAbsent` assertions called `getByRole().isVisible()` directly, bypassing the resolver's cache/heal ladder entirely, with a strict-mode violation on 2+ matches swallowed by `.catch(() => false)` into a silently-inverted verdict; (4) `Tier1Target.role` was an unconstrained `z.string()`, so a DOM-blind authoring agent guessing a non-ARIA role fails silently at runtime instead of at schema validation, and `element_appears` was the one `ExpectedOutcome` variant taking a raw CSS selector rather than a `Tier1Target`, breaking the DOM-blind authoring contract by construction; (5) `apiBody`/`dbRow` assertions compared via `JSON.stringify`, false-failing on key reordering; (6) `characterizePage`'s `repeatedStructure` signal was computed but never read anywhere, dead in exactly the highest-risk scenario (repeated-row lists) for false ties; (7) `GimbalConfig.bands` had no `high > medium` ordering constraint, so a misconfigured config could silently invert confidence semantics.

**Decision:** (1) `act.ts`'s `navigate` case now compares `origin+pathname` of the intended URL against `page.url()` after `goto()` resolves, throwing if they differ; `grounding/index.ts` catches that throw for non-target (navigate/wait) steps and sets `stoppedAt` on the step rather than propagating an uncaught rejection, consistent with the existing low-confidence stop path. (2) `dom-extractor.ts` now computes `parentXpath` (the immediate parent's own xpath) alongside the existing `contextPath`; `banding.ts`'s `tiebreak` keys its `sameParent` check on `parentXpath` equality instead of `contextPath[0]`. (3) `assert.ts` gained `evaluateElementPresence`, which calls `.count()` before `.isVisible()` and returns an explicit `{ok: false, reason: "ambiguous target..."}` on 2+ matches instead of silently resolving to a boolean; full routing through `locate.ts`'s cache/heal ladder was scoped out since assertion targets, unlike action-step targets, are never grounded to their own artifact record — noted as a larger architectural gap, not fixed here. (4) Added `AriaRole`, a Zod enum of Playwright's `getByRole()`-recognized ARIA roles, and changed `Tier1Target.role` to use it; changed `ExpectedOutcome`'s `element_appears` variant from `{value: z.string()}` to `{target: Tier1Target}` (a breaking schema change to `spec.json`/`grounded.json`, confirmed with the user before proceeding — no automatic migration provided) and routed it through the same `evaluateElementPresence` helper. (5) Added a recursive `deepEqual` (key-order-independent, array-aware) in `assert.ts` and swapped it in for both `apiBody` and `dbRow`. (6) `computeWeights` in `router.ts` now adds a `+0.15` structure-weight boost when `page.repeatedStructure` is true, on the same pattern as the existing `iconRatio`/`textDensity`/`hasForm`/`hasModal` adjustments — repeated rows are where semantic similarity is least discriminating and position/structure is what banding's existing siblingIndex tiebreak can actually use. (7) `GimbalConfig.bands` gained a `.refine((b) => b.high > b.medium)` check. All seven fixes shipped with new/updated unit tests (`act.test.ts`, `banding.test.ts`, `dom-extractor.test.ts`, `assert.test.ts`, `router.test.ts`, new `config.test.ts`); full workspace build and 300-test core/shared suite green afterward.

**Rationale:** Each fix targets a place where a plausible-looking result was being produced without the information needed to know it was wrong — a redirect that "succeeded," a tiebreak that "resolved," an assertion that "passed" on a strict-mode swallow, a role that "matched" nothing. Given the project's deterministic-first, no-silent-guessing philosophy (banding already downgrades rather than guesses on genuine ambiguity), the consistent fix shape was to either detect the specific failure mode explicitly and surface it, or make the disambiguating data actually distinguish what it was meant to distinguish. The full `locate()` routing for assertion targets (part of finding 3) and the `element_appears` schema break (finding 4) were flagged to the user rather than assumed, since both cross from "bug fix" into "architecture/compatibility decision" territory.
